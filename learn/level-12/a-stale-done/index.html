12.4 A stale done

Teaches Run handshake (primitive). About 6 minutes.

On the board, the decoder sits in a harness: a UART receives a frame from the computer, here one whole input for the decoder, many bytes long (lesson 10.3's frame was one byte). The harness starts the core on it, and when the core has finished, it sends back the core's decisions and the number of cycles the core counted.

Busy, then done

The core has a start input and two outputs, as lesson 5.4's controller does: busy while it works, and done once it has finished. done stays 1 after a run, until the next run begins.

The first harness pulsed start and then waited for done. But a core takes time to begin, and until it had, done was still 1 from the last run. The harness took that stale done and sent back the previous frame's decisions. The fix waits for busy first, and takes done only after it.

The bug hid while every run used the same frame, because the old decisions were the right ones. Over 300 runs that alternated between two frames it showed now and then (the small model below shows it on every run after the first), and a re-run of the simulation without the fix failed the same way. With the fix, the later builds each passed 1,000 runs on the board over 67 different frames: every decision right, and the same count of cycles every time.

In small

run_ctl (Listing 1) pulses start, waits in WAIT_BUSY until busy is 1, then in WAIT_DONE until done is 1, and pulses reply. Its core in the testbench, slot_core, takes a cycle to begin, then sets busy and clears done, and works for a set number of cycles a run. In Figure 1 it begins its second run with done still 1 from the first.

Questions

Question 1 of 3. Predict reply

Lesson 12.4's run_ctl drives a core that works for 4 cycles a run. This is the core's first run since the reset, so done starts at 0. Cycles 0 and 1 are drawn for you. Set reply for the rest.

Question 2 of 3. Predict reply

Lesson 12.4's run_ctl drives a core that works for 6 cycles a run. The core finished a run just before this one, so done is still 1. Set reply for every cycle.

Question 3 of 3. Find the bug

run_ctl_bug should reply once each run is over, as lesson 12.4's run_ctl does. Its testbench passes the core's first run, then fails on the second, for the frame 20: the reply comes before the core has been busy, with the result 11, the first run's (both in hexadecimal). Show answer and explanation

The bug is on line 29, state <= WAIT_DONE;. It should read state <= WAIT_BUSY;.

After start, this controller waits for done at once. After a reset done is 0, so the first run works; after a run it is still 1, so the controller replies at the next edge, before the core has even begun, with the last frame's result. It must wait for busy first, and take done only after it has seen busy.
