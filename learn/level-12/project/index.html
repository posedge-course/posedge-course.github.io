Level 12

Level 12 project Time a core on the board

Write harness in my_harness.sv until harness_tb.sv prints TEST PASSED; on the board, every key you type comes back as its code plus 1, with the core's count of cycles, the same every time. About 60 minutes in simulation.

The case study ends where the thesis's measurements were made: on the board. Your harness receives a byte from the computer, starts a core on it through lesson 12.4's run_ctl, and sends back the core's result and the core's count of cycles, as the 3D decoder's harness sends back its decisions and its cycle counter. The core, slot_core, stands in for the decoder: a run of 3,456 cycles of work, one slot of a hidden engine (lesson 12.3).

ParameterDefaultWhat it sets

The file you write is my_harness.sv; the module inside is harness, the name the testbench uses. The testbench sets LAST to 7, so a bit lasts 8 cycles, and sends its bytes from a clock of its own.

What Vivado built

Listing 1 is the Slice Logic table of the course's build. The whole harness, two UARTs, the controller and the core, takes 107 of the chip's 63,400 LUTs. Listing 2 is the last line of its Design Timing Summary.

What you see when it works

  • The run prints TEST PASSED. The frames A, B, A, B and z each get a reply: their code plus 1 in hexadecimal, then 00000D82, 3,458 cycles: the 3,456 of work, the cycle the core takes to begin, and the edge that sets done. A 1 that arrives while the reply to 0 goes out gets no reply.
  • With the board: each key comes back at once as a line like 42 00000D82, and the count is the same for every key. LD4 lights after the first run.

If it fails

  • syntax error, followed by Invalid module instantiation: the command lacks -g2012. Add it.
  • Unknown module type: harness: the module in my_harness.sv has another name. It must be called harness.
  • error: Unknown module type: slot_core, or the same for another part, after a file's name and a line number: a file is missing from the command. All eight must be named.
  • TEST FAILED: frame A: the reply was "", expected "42 00000D82\r\n" at 102927 ns: nothing came back. Check that uart_rx's valid reaches run_ctl's go, and that tx comes from uart_tx.
  • TEST FAILED: frame A: the reply was "4", expected "42 00000D82\r\n" at 102927 ns: the reply moved on while uart_tx was busy, so only its first character went out. Move on only when uart_tx is not busy.
  • TEST FAILED: frame A: the reply was "444444444444444", expected "42 00000D82\r\n" at 48027 ns: the reply starts again every cycle. Start it once, when reply pulses, not whenever done is 1.
  • TEST FAILED: frame A: the reply was "42 0000D820\r\n", expected "42 00000D82\r\n" at 48027 ns: the space used up a digit. The digits must wait while the space goes out.
  • TEST FAILED: frame A: the reply was "42 00000N82\r\n", expected "42 00000D82\r\n" at 48027 ns: the letters are out of place. A is 41, so a digit from 10 to 15 is 37 plus the digit, in hexadecimal.
  • TEST FAILED: frame A: the reply was "42 00000=82\r\n", expected "42 00000D82\r\n" at 48027 ns: a digit over 9 went out as 30 plus the digit. 10 to 15 must be the letters A to F.
  • TEST FAILED: frame A: the reply was "00 000D8242\r\n", expected "42 00000D82\r\n" at 48027 ns: the result and the count are the wrong way round. The result's two digits come first.
  • TEST FAILED: 1 came during a reply, and got one at 337527 ns: a byte that arrived while a reply went out still started the core. It may be run_ctl's go only while no reply is going out.

These messages are from Icarus Verilog 12.

On the board (optional)

You need an Arty A7 and Vivado for this part. Everything above works without them.

The board steps use Vivado's project mode, as in the earlier projects. If nothing comes back, check that the terminal is open on the board's serial port at 115,200 baud. The count is the core's own: it is the same for every key, as the thesis's decoders counted the same number of cycles on every board run of a given size. It covers the core alone: the reply's 13 characters take about 1.1 ms at 115,200 baud, more than 30 times the core's run. The thesis's decoder is the same: a frame's round trip over the UART takes far longer than the core.

Your checklist

Simulation path

  1. Make a new folder and save the eight files listed above into it. harness_tb.sv is the specification: it plays the computer, sending bytes and reading the replies. harness.xdc is for the board path. You may use your own my_uart_tx.sv from level 5: name it in place of uart_tx.sv in the run step and in the Vivado project.
  2. Make a file my_harness.sv with a module named harness, the three parameters in the second table with their defaults, and the five ports in the first.
  3. Turn btn into a reset, rst, with a rst_sync (lesson 9.4), and place a uart_rx (lesson 10.3) on rx, with BITS set to TBITS and LAST to LAST.
  4. Place a run_ctl (lesson 12.4) and a slot_core with SLOT set to SLOT. The core's frame is the byte uart_rx received, and its start, busy and done go to and from run_ctl. A received byte is the controller's go, but only while no reply is going out.
  5. When run_ctl pulses reply, keep the core's result and cycles to send. The reply is 13 characters: result as two hexadecimal digits, a space, cycles as eight hexadecimal digits, then CR (0D, carriage return) and LF (0A, line feed). In ASCII, the digits 0 to 9 are 30 to 39, and A to F are 41 to 46.
  6. Place a uart_tx (level 5's) with BITS and LAST set as for the receiver. While a reply is going out, pulse send with its next character each time uart_tx is not busy. Make led the core's done.
  7. Run iverilog -g2012 -o harness_sim harness_tb.sv my_harness.sv run_ctl.sv slot_core.sv uart_rx.sv uart_tx.sv sync2.sv rst_sync.sv, then vvp harness_sim, until it prints TEST PASSED.
  8. Open harness_tb.vcd and add rx and tx, and from your harness start, busy, done and reply. Find the second run: done is still 1 from the first when start pulses, and reply waits for the end of the run.

On the board (optional)

  1. In Vivado, create an RTL project for xc7a100tcsg324-1 with my_harness.sv, the six other design files of the run step, and the saved harness.xdc. Make harness the top module, then run Generate Bitstream.
  2. Open the timing summary and check that every constraint is met, then compare the utilisation report with Listing 1.
  3. Program the board, then open a serial terminal on the board's serial port at 115,200 baud, 8 data bits, no parity and 1 stop bit (level 7's project).
  4. Type A: the board replies 42 00000D82, the code after A's 41, and the core's count of cycles, and LD4 lights. Type B, then A again: the result follows the key; the count never changes.
