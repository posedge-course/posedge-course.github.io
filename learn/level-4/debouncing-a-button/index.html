4.4 Debouncing a button

Teaches Debouncer (design). About 5 minutes.

Press a button and its metal contacts do not close cleanly. For up to a few milliseconds they bounce, touching and parting, so the signal flips between 0 and 1 before it settles; letting go bounces too. At 100 MHz a millisecond is 100,000 cycles, so an edge detector on the bare button would see a burst of presses.

A debouncer believes a change only once it has lasted long enough. Listing 1 is one.

Two flip-flops first

A button can change at any moment, even right at a clock edge. So btn first goes through sync0 and sync, a 2-bit shift register, and the rest of the design reads sync: a copy that changes only at rising edges, two edges after btn does. Level 9 explains why it takes two.

Count while it differs

stable is the debouncer's answer. At each edge where sync differs from stable, count goes up by one. Where they agree again, count goes back to 0, so every bounce starts the count afresh. At an edge where count is HOLD and they still differ, stable takes sync's value. So stable changes only after sync has differed from it at HOLD + 1 edges in a row. With HOLD at 999,999 that is a million edges, 10 ms at 100 MHz, which outlasts the bounces.

Figure 1 is a simulation with HOLD set to 2, so that a press fits in a few cycles.

One press, one pulse

stable is a clean level, and lesson 4.3's edge detector turns each rise of it into a single pulse. Level 4's project joins the two into a module called press, one pulse for each press of a button.

Show answer and explanation

The bug is on line 26, count <= count; // agrees again. It should read count <= '0;.

When sync agrees with stable again, count keeps its value instead of going back to 0. So the edges of every short bounce add up, and a press that never stayed put for HOLD + 1 edges in a row still reaches the count. Written count <= '0;, every bounce starts the count afresh (lesson 4.4). The HOLD line is not the cause: a larger HOLD would only make enough bounces take longer to add up.
