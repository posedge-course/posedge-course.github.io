8.3 Reading a timing report

Teaches Timing report (design). About 5 minutes.

Every build in this course ends with a timing summary, timing_summary.rpt. It reads from the top down:

  1. check_timing: what could stop a path from being checked at all, such as registers with no clock (lesson 7.2).
  2. Design Timing Summary: WNS, TNS and the failing endpoints for setup (lesson 8.2), then the same for hold, where WHS (worst hold slack) is the smallest hold slack.
  3. Clock Summary: each clock with its period and frequency, as the constraints say.
  4. The paths, under Timing Details, clock by clock and worst first: the setup checks under Max Delay Paths, the hold checks under Min Delay Paths.

One path's header

Each path starts with a header: Listing 1 is that of msum16's worst path, its critical path (lesson 8.2).

  • Slack is the path's slack, worked out at the end of the path's lines.
  • Source and Destination are where the path starts, a flip-flop's clock pin C, and where it ends, a flip-flop's D. Vivado names each register after your code, with _reg added: x_reg[12][2] is bit 2 of x[12].
  • Requirement is the time the path is allowed: here one period, edge to edge.
  • Data Path Delay is how long the data takes from the source's clock pin to the destination's D, split into logic, the time inside cells, and route delay, the time in the wires between them.
  • Logic Levels counts the cells of logic between the two flip-flops, each kind in brackets. Each cell is one logic level.
  • Clock Path Skew is how much later the clock edge reaches the destination than the source: clock skew. Clock Uncertainty is an allowance for jitter, the small random wobble in when each clock edge arrives. Both move the required time a little.

Below the header come the clock's path to the source flip-flop, through its buffers; one line for each cell and wire of the data, in the order the data meets them, with its delay; then the clock's path to the destination, and the sum: required time, arrival time and slack.

Reading it for a failing path

For a design that misses timing, start at the worst path's header. Source and Destination point at the lines of your code the path runs between, and Logic Levels and the split between logic and wires say where its time goes. A path through many cells can be given fewer of them between two edges, which is lesson 8.4.

Questions

Question 1 of 3. Read the report

msum16 is lesson 8.2's sum of the last 16 samples, built for the board's 100 MHz clock. Below is the header of its worst path, the one with the least slack.

vivado/reports/msum16/arty-a7-100t/timing_summary.rpt, lines 203 to 212. Written by Vivado.

203Slack (MET) :             0.435ns  (required time - arrival time)204  Source:                 x_reg[12][2]/C205                            (rising edge-triggered cell FDRE clocked by sys_clk_pin  {rise@0.000ns fall@5.000ns period=10.000ns})206  Destination:            y_reg[17]/D207                            (rising edge-triggered cell FDRE clocked by sys_clk_pin  {rise@0.000ns fall@5.000ns period=10.000ns})208  Path Group:             sys_clk_pin209  Path Type:              Setup (Max at Slow Process Corner)210  Requirement:            10.000ns  (sys_clk_pin rise@10.000ns - sys_clk_pin rise@0.000ns)211  Data Path Delay:        9.606ns  (logic 4.805ns (50.023%)  route 4.801ns (49.977%))212  Logic Levels:           14  (CARRY4=7 LUT3=3 LUT4=2 LUT5=1 LUT6=1)

How many cells of logic does msum16's worst path pass through?

Show answer and explanation

The report says 14.

Read Logic Levels: 14, and in brackets how many of each kind: 7 CARRY4s and 7 LUTs. The sum of 16 samples needs several additions one after another between the two flip-flops, and each brings its own LUTs and carry chain.

Question 2 of 3. Put the steps in order

msum16's worst path starts at x_reg[12][2], a flip-flop of the samples, ends at y_reg[17], and passes through 14 cells of logic between them. Put in order what the data passes through.

  • The sum reaches y_reg[17]'s D input.
  • More LUTs and CARRY4s add the sums so far.
  • The clock edge reaches x_reg[12][2], and its Q changes.
  • A LUT3, then a LUT4, take bits of the samples.
  • Three CARRY4s add them, four bits at a time.
Show answer and explanation

In order:

  1. The clock edge reaches x_reg[12][2], and its Q changes.
  2. A LUT3, then a LUT4, take bits of the samples.
  3. Three CARRY4s add them, four bits at a time.
  4. More LUTs and CARRY4s add the sums so far.
  5. The sum reaches y_reg[17]'s D input.

A path starts at a flip-flop's clock and ends at a flip-flop's D. In between, each addition takes its LUTs first, which feed the carry chain's inputs (lesson 6.2), then its CARRY4s, and the next addition takes that sum in. The tempting slip is CARRY4s before LUTs: the LUTs work out what the carry chain adds.

Question 3 of 3. Read the report

msum32 adds 32 samples where lesson 8.2's msum16 adds 16, and misses the 100 MHz clock. Below is the header of its worst path.

vivado/reports/msum32/arty-a7-100t/timing_summary.rpt, lines 203 to 212. Written by Vivado.

203Slack (VIOLATED) :        -0.500ns  (required time - arrival time)204  Source:                 x_reg[10][3]/C205                            (rising edge-triggered cell FDRE clocked by sys_clk_pin  {rise@0.000ns fall@5.000ns period=10.000ns})206  Destination:            y_reg[20]/D207                            (rising edge-triggered cell FDRE clocked by sys_clk_pin  {rise@0.000ns fall@5.000ns period=10.000ns})208  Path Group:             sys_clk_pin209  Path Type:              Setup (Max at Slow Process Corner)210  Requirement:            10.000ns  (sys_clk_pin rise@10.000ns - sys_clk_pin rise@0.000ns)211  Data Path Delay:        10.559ns  (logic 4.592ns (43.489%)  route 5.967ns (56.511%))212  Logic Levels:           14  (CARRY4=7 LUT3=3 LUT4=2 LUT5=1 LUT6=1)

How long does the data of msum32's worst path spend in wires, in nanoseconds?

Show answer and explanation

The report says 5.967 ns.

Read Data Path Delay: route 5.967 ns of 10.559. The path passes through as many cells as msum16's, 14 of the same kinds, and its logic takes about as long, 4.592 ns against 4.805. The wires take 5.967 ns against 4.801: the extra time, and more, is in the wires.
