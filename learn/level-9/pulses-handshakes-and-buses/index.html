9.3 Pulses, handshakes and buses

Teaches Pulse crossing (circuit), Handshake (circuit). About 6 minutes.

A synchroniser carries a level. A pulse one cycle of a fast clock long can come and go between two edges of a slow one, and never be seen.

A pulse crosses as a level

pulse_cross (Listing 1) turns each pulse into a change of level. level_a is a toggle: it flips at every pulse_a, then holds still. The reading side synchronises it into level_b, and keeps last_b, level_b as it was one edge ago. When the two differ, the level has just flipped, so pulse_b is 1 for one cycle of clk_b. Pulses must come at least two cycles of clk_b apart, or the synchroniser could miss a flip.

^ is exclusive or: 1 when its two sides differ. So level_a ^ pulse_a is level_a flipped when pulse_a is 1, and kept as it is when pulse_a is 0.

A value crosses with a handshake

A whole value cannot cross bit by bit, because its bits can arrive at different edges (lesson 9.2). It can cross while it is held still. hs_cross does this with two signals, req and ack, each through its own synchroniser, in a handshake. The sending side holds the value and raises req. The receiving side, seeing req, takes all eight bits at once, steady by then, and answers by raising ack. Then the two signals go back down, each side again waiting to see the other's change, before the next value can go.

Nothing reads the value while it changes, so no bit can arrive early. The price is speed: every value waits for two crossings each way. In hs_cross_tb, with clocks of 10 ns and about 33 ns, each value takes about 200 ns.

Questions

Question 1 of 3. Predict pulse_b

This is lesson 9.3's pulse_cross, with clk_b drawn as the cycles. pulse_a, one cycle of the faster clk_a, flips level_a in cycle 0. Cycles 0 and 1 are drawn for you. Set pulse_b for the rest.

Question 2 of 3. Put the steps in order

hs_cross carries an 8-bit value from clk_a's side to clk_b's with a handshake: req crosses one way and ack the other, each through a synchroniser. Put in order one value's round trip.

  • clk_a's side sees ack fall, and may send the next value.
  • clk_a's side sees ack and lowers req.
  • clk_b's side sees req, takes the value and raises ack.
  • clk_b's side sees req fall and lowers ack.
  • clk_a's side holds the value still and raises req.
Show answer and explanation

In order:

  1. clk_a's side holds the value still and raises req.
  2. clk_b's side sees req, takes the value and raises ack.
  3. clk_a's side sees ack and lowers req.
  4. clk_b's side sees req fall and lowers ack.
  5. clk_a's side sees ack fall, and may send the next value.

Each step waits to see the one before it, through a synchroniser. The value is held from the edge at which req rises until ack comes back, so clk_b's side can take all eight bits at once. The tempting slip is to send the next value as soon as ack rises: the round trip ends only when both req and ack are down again.

Question 3 of 3. Find the bug

pulse_cross_bug should carry each one-cycle pulse of clk_a to clk_b as one pulse, as lesson 9.3's pulse_cross does. Its testbench, the one pulse_cross passes, fails: after the first pulse, none has come out. Pick the line that is wrong.

hdl/level-09/pulse_cross_bug/pulse_cross_bug.sv, lines 14 to 20

  • 14 logic level_a; // flips at each pulse_a
  • 15 logic level_b; // level_a, synchronised to clk_b
  • 16 logic last_b; // level_b, one edge of clk_b ago
  • 17
  • 18 always_ff @(posedge clk_a)
  • 19 if (rst_a) level_a <= 1'b0;
  • 20 else level_a <= pulse_a;
Show answer and explanation

The bug is on line 20, else level_a <= pulse_a;. It should read else level_a <= level_a ^ pulse_a;.

level_a should flip at each pulse, level_a ^ pulse_a. As written it takes pulse_a itself, one 10 ns cycle of clk_a, and clk_b's edges come about every 33 ns, so most pulses fall between two of them and are never seen. A pulse that is caught shows as two changes of level_b, one up and one down, so it comes out twice.
