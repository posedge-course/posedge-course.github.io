0.4 The tools and what each does

Teaches Simulation and build tools (design). About 5 minutes.

A build takes minutes and cannot show what the design does without a board. A simulator runs your design's code on your computer as if it were hardware: in seconds, with every signal visible. So you check a design in simulation first. Figure 1 shows which file goes into which tool.

The testbench

A testbench is a second module that sets the design's inputs over time and checks its outputs. It is never built into hardware. In Listing 1:

  • The line that starts vote dut puts one vote inside the testbench: the design under test.
  • Each step line is one row: the inputs a, b and c, then the y it expects. 1'b1 means one bit set to 1, and 1'b0 one bit set to 0.
  • step is a task, a named list of testbench lines you can use again. It sets the inputs, waits 10 ns with #10, then compares y with the expected value. !== means "differs from". A difference prints a line starting TEST FAILED, with the time.
  • At the end it prints TEST PASSED if no row failed.

Running it

This course's simulator is Icarus Verilog. iverilog compiles the design and the testbench together, and vvp runs the result. $dumpfile names the waveform file the run writes, a VCD (value change dump) file, and a waveform viewer such as Surfer or GTKWave draws it. Every waveform on this site comes from such a file.

When a row fails, its TEST FAILED line gives the time at the end of that step, when the check ran. In the waveform, look at the 10 ns just before that time, find the signal that is wrong, and follow it back to the line that drives it. Fix it, then compile and run again.

The other tools

Verilator is a simulator that can also check code without running it, called lint, which is how this course uses it: it warns about likely mistakes. Every correct example on this site passes it; some broken ones are there to show its warnings. But neither a clean lint nor a finished build tells you that y is right. Only a testbench does.

In this course Vivado, AMD's tool for this FPGA, builds the bitstream. It is a very large download and does not run on macOS. On a Mac you can still do every lesson and every project's simulation path.

You install Icarus and a viewer in this level's project, and Vivado in the optional board path of level 1's project.

  • Compile both files together with iverilog.

  • Run the result with vvp: the testbench prints its verdict and writes the waveform file.

In order:

  1. Save vote.sv and vote_tb.sv in one folder.
  2. Compile both files together with iverilog.
  3. Run the result with vvp: the testbench prints its verdict and writes the waveform file.
  4. Open the waveform file in a viewer and look at a, b, c and y.

iverilog turns the design and its testbench into one simulation, and vvp runs it. The run writes the waveform file as it goes, so the viewer comes last: it can only draw what the run recorded.

Question 2 of 3. Fill the blank

vvp has run this testbench. Type the name of the file your waveform viewer should open.

hdl/level-00/vote/vote_tb.sv, lines 25 to 28

25 initial begin
26 $dumpfile("(blank)");
27 $dumpvars(0, vote_tb);
28 errors = 0;
Show answer and explanation

The blank is vote_tb.vcd.

$dumpfile names the waveform file the run writes, here vote_tb.vcd, and $dumpvars records every signal of vote_tb in it. A VCD file lists each change of each signal with its time, and the viewer draws those changes.

  • See that y is 0 there, although a and b are both 1.
  • Open the waveform file in the viewer.

In order:

  1. Open the waveform file in the viewer.
  2. Look at the step that ends at 20 ns, from 10 ns to 20 ns.
  3. See that y is 0 there, although a and b are both 1.
  4. Find the line of vote.sv that drives y, and correct it.
  5. Compile with iverilog, then run with vvp, until the verdict is TEST PASSED.

The time in a TEST FAILED line is when the check ran, at the end of the failing step, so the row to look at is the 10 ns before it. The waveform shows which signal is wrong there; you follow it back to the line that drives it and correct that line. Then you compile again before you run: vvp alone would run the old simulation, built from the old vote.sv.
