3.4 What simulates but cannot be built

Teaches Synthesisable code (primitive). About 5 minutes.

Lesson 3.1's testbench used #5, initial, $display and $finish. They tell the simulator what to do and when, and a testbench is never built, so it may use anything. A design file is built, and synthesis builds only what the FPGA's cells can do. Code it can build is synthesisable.

A delay that vanishes

In simulation, Listing 1 lights the LED 20 ns after the button changes. Synthesis drops the delay. Figure 1 shows what it builds: a pin buffer in, a pin buffer out, and a wire between them. Real delays come from the cells and the wiring, and Vivado checks that they are short enough for the clock (level 8). To make something happen later on purpose, you count clock cycles (level 4).

Lines that build nothing

$display and $finish build nothing; Vivado even prints a $display while it reads the file. An initial line that gives a register a value does reach the FPGA: Vivado makes it that flip-flop's starting value. This course states starting values with a reset instead (lesson 2.3), which also lets you start again, so initial stays in testbenches.

Code that is refused

Some code simulates but cannot be built at all. A flip-flop is built to act on one edge of its clock. A block that asks to act on both edges of the same clock runs in the simulator, but synthesis refuses it: no flip-flop has an input for that. An asynchronous reset (lesson 2.3) is different. It adds a second signal to the event list, and the flip-flop's CLR input handles it.

So design files use logic, assign, always_comb, and always_ff on one edge of one clock, plus an asynchronous reset where you need one. This course lints every design with Verilator and runs every testbench; the designs a lesson draws or quotes are also synthesised.

The report says 0.

Read the Used column of the Slice LUTs row, then of the Slice Registers row. Synthesis drops the delay, so led is joined to btn by a wire from one pin buffer to the other, with no logic and no flip-flop between (lesson 3.4). A real delay on purpose would need flip-flops counting clock cycles, and this design has no clock.

Question 3 of 3. Find the bug

This file simulates, and its testbench passes. q_rise should copy d at each rising edge and clear at once when rst rises; q_both should copy d at both edges of clk. Synthesis refuses to build it. Pick the line that is wrong.

hdl/level-03/fast_copy_bug/fast_copy_bug.sv

  • 1// Two copies of d. q_rise copies d at each rising edge of clk, and rst
  • 2// clears it at once. q_both copies d at both edges of clk.
  • 3module fast_copy_bug (
  • 4 input logic clk,
  • 5 input logic rst,
  • 6 input logic d,
  • 7 output logic q_rise,
  • 8 output logic q_both
  • 9);
  • 10 always_ff @(posedge clk or posedge rst) begin
  • 11 if (rst) q_rise <= 1'b0;
  • 12 else q_rise <= d;
  • 13 end
  • 14
  • 15 always_ff @(posedge clk or negedge clk) begin
  • 16 q_both <= d;
  • 17 end
  • 18endmodule
Show answer and explanation

The bug is on line 15, always_ff @(posedge clk or negedge clk) begin. It should read always_ff @(posedge clk) begin.

The second block asks one flip-flop to act on both edges of the same clock, and a flip-flop is built for one edge, so synthesis refuses it: Yosys stops with "Multiple edge sensitive events", and Vivado refuses it too (lesson 3.4). The first block also has two events, but the second is a reset on another signal, which the flip-flop's CLR input handles (lesson 2.3), so it builds. Written always_ff @(posedge clk) begin, the second block builds, but copies only once per cycle. To copy twice per cycle you need a clock twice as fast, or special cells at the FPGA's pins that use both edges.
