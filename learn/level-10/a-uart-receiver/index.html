10.3 A UART receiver

Teaches UART receiver (design). About 6 minutes.

Level 5's uart_tx sends a byte as a frame: the line rests at 1, then a start bit, 0, the eight data bits, bit 0 first, and a stop bit, 1, each 868 cycles long at 115,200 baud. A receiver has no clock from the sender: all it has is the line, and when it changes.

Finding the bits

The line comes from another chip, so it is an asynchronous input: uart_rx passes it through a synchroniser first (lesson 9.2) and calls the result line. Then it waits for line to fall: the start bit has begun. It waits half a bit, to stand in the middle of the start bit, and checks that line is still 0; if not, it was a short dip, not a byte. From there, every whole bit is the middle of the next bit, and it reads each of the eight data bits there. A whole bit after the last comes the stop bit. If line is 1 there, the framing is right: valid is 1 for one cycle with the byte on data. If not, the byte is dropped.

In Listing 1, timer counts the cycles since the falling edge or the last read; a bit lasts LAST + 1 of them, 868 on the board, so LAST >> 1 (lesson 9.4) is half a bit. mid is 1 in the cycle line is read: half a bit after the falling edge while in START, a whole bit after the last read otherwise. line_was is line one cycle ago, so line_was & ~line is 1 just after line falls, and index counts the data bits.

Why the middle

The sender's clock and the receiver's are two different clocks, a little apart. For each bit the receiver counts 868 of its own cycles, which may be slightly more or less than the sender's bit, and the difference adds up, bit after bit, until the stop bit. Reading in the middle leaves almost half a bit of room either way. uart_rx_tb sends some bytes 3% slower and some 3% faster than the receiver expects, and every byte arrives.

Questions

Question 1 of 3. Put the steps in order

Put the steps of uart_rx receiving one byte in order.

  • Wait a whole bit, and check the stop bit is 1.
  • Wait half a bit, and check the line is still 0.
  • Read bits 1 to 7, a whole bit apart.
  • Wait a whole bit, and read bit 0.
  • Wait for the synchronised line to fall.
Show answer and explanation

In order:

  1. Wait for the synchronised line to fall.
  2. Wait half a bit, and check the line is still 0.
  3. Wait a whole bit, and read bit 0.
  4. Read bits 1 to 7, a whole bit apart.
  5. Wait a whole bit, and check the stop bit is 1.

The fall starts the start bit. Half a bit later the receiver stands in its middle, where a real start bit is still 0 and a short dip is already over. Each whole bit after that is the middle of the next bit: bit 0, bits 1 to 7, then the stop bit, which must be 1 for the byte to count.

Question 2 of 3. Fill the blank

A UART sends bit 0 first. Fill in how uart_rx takes the bit it reads into data, so that after the eighth read, bit 0 is data[0] and bit 7 is data[7].

hdl/level-10/uart_rx/uart_rx.sv, lines 57 to 64

57 always_ff @(posedge clk)
58 if (state == START) begin
59 index <= 3'd0;
60 data <= 8'h00;
61 end else if ((state == DATA) & mid) begin
62 data <= (blank);
63 index <= index + 3'd1;
64 end
Show answer and explanation

The blank is {line, data[7:1]}.

{line, data[7:1]}: the bit just read goes in at the top, and the others move down one place. Bit 0, read first, moves down seven times and ends in data[0]; bit 7, read last, stays at the top. {data[6:0], line}, shifting the other way, would turn every byte back to front.

The bug is on line 33, assign mid = (timer == LAST);. It should read assign mid = (state == START) ? (timer == (LAST >> 1)) : (timer == LAST);.

42 is 0100_0010 and A1 is 1010_0001: every bit came out one place down, with a 1, the stop bit, on top. Each read came half a bit late, at the start of the next bit instead of the middle of its own. In START, mid must come half a bit after the falling edge, timer == (LAST >> 1); as written it waits a whole bit there too.
