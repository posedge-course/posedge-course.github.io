7.4 Works in simulation, dead on the board

Teaches Board checklist (design). About 5 minutes.

A testbench proves that your code does what the testbench expects. When the board then does nothing, the difference lies between the testbench and the board, and each stage of the build is a place to look. Go in the order the build goes, and each check rules out a whole stage before the next.

  1. The testbench. Run it once with the parameters the board build uses, not only with the small ones that keep a simulation short, and drive each input as the board drives it.
  2. The Utilization report that synthesis writes: no latch (lesson 6.4), and your logic all there, none of it removed because nothing reads it (lesson 6.1).
  3. The timing summary after place and route: a create_clock for the board's clock, and every constraint met (lesson 7.2).
  4. The pins: each port on the pin the board wires to its part, with its I/O standard (lesson 7.1). The bitstream step stops a port with no pin or no standard, but it cannot know your board: check each pin against the master XDC yourself.
  5. The board: DONE lit after programming, and for a serial line, a terminal at the design's baud rate (lesson 7.3).

Inputs as the board drives them

The Arty's four push buttons are active high: each reads 1 while it is pressed and 0 the rest of the time. Some inputs are active low, reading 0 while pressed, like the Arty's red RESET button. Listing 1 is tick_led's register, whose rst is BTN0: it resets while rst is 1, so the LED is held off only while the button is down.

A reset written for the other kind of button holds the design in reset for as long as nobody touches it. Its own testbench can still pass, if it drives the reset the same wrong way. The fix is in the testbench too: drive rst at 0 except for short presses, as the board will, and a reset written the wrong way fails there instead of on the board.

Questions

Question 1 of 3. Put the steps in order

After programming, LD4 stays dark, though your design passes its testbench. Put these checks in the order the build reaches them, from your desk to the board.

  • Check every port's pin against the master XDC.
  • Read the timing summary that place and route writes.
  • Run the testbench with the parameters the board build uses.
  • Program the board and check that DONE lights.
  • Read the Utilization report that synthesis writes.
Show answer and explanation

In order:

  1. Run the testbench with the parameters the board build uses.
  2. Read the Utilization report that synthesis writes.
  3. Read the timing summary that place and route writes.
  4. Check every port's pin against the master XDC.
  5. Program the board and check that DONE lights.

The testbench runs before Vivado does anything. Synthesis writes its Utilization report before place and route can time the design. The bitstream step comes after routing, and it checks only that each port has a pin and a standard, so whether each pin is the right one is yours to check there. DONE can light only once the board is programmed. Checking in this order, each check rules out a whole stage.

Question 3 of 3. Find the bug

tick_led_bug should change LD4 every half second and keep it off while BTN0 is held down. Its author tested it with rst held at 0 to reset it, and it passed. On the board LD4 never lights. Its testbench here drives rst as BTN0 does, 1 only while pressed, and fails. Pick the line that is wrong.

hdl/level-07/tick_led_bug/tick_led_bug.sv

  • 1// LED led should change once in every LAST + 1 cycles of clk, as in
  • 2// tick_led. rst is button BTN0, which reads 1 while it is pressed and 0
  • 3// the rest of the time: holding BTN0 down should keep led off.
  • 4module tick_led_bug #(
  • 5 parameter int BITS = 26,
  • 6 parameter logic [BITS-1:0] LAST = 49_999_999
  • 7) (
  • 8 input logic clk,
  • 9 input logic rst, // BTN0: 1 while pressed
  • 10 output logic led
  • 11);
  • 12 logic tick;
  • 13
  • 14 tick_gen #(.BITS(BITS), .LAST(LAST)) ticker (
  • 15 .clk(clk), .rst(rst), .tick(tick)
  • 16 );
  • 17
  • 18 always_ff @(posedge clk) begin
  • 19 if (~rst) led <= 1'b0;
  • 20 else if (tick) led <= ~led; // changes only at a tick
  • 21 end
  • 22endmodule
Show answer and explanation

The bug is on line 19, if (~rst) led <= 1'b0;. It should read if (rst) led <= 1'b0;.

if (~rst) led <= 1'b0; resets led while rst is 0, which is all the time BTN0 is up, so LD4 is held dark. BTN0 reads 1 only while pressed, so the reset must test rst itself, as tick_led does. The author's testbench passed because it drove rst the same wrong way the code expected.
