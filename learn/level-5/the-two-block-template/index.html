5.2 The two-block template

Teaches Next-state logic (primitive). About 5 minutes.

Lesson 5.1's door decides and remembers in one always_ff block. Most state machines are written in two blocks instead, one for each job, as in Listing 1. It is the same door.

Next-state logic

The always_comb block is the next-state logic: from state and the inputs it works out next, the state the door will go to at the next rising edge. It is logic, like lesson 1.3's blocks, so next changes as soon as an input or the state does.

Its first line, next = state;, is a default assignment (lesson 1.4). The case below changes next only where a transition applies, so wherever none does, the door stays in its state. And since every path gives next a value, the block builds no latch.

The state register

The always_ff block is the state register. At each rising edge it takes next, or CLOSED when rst is 1. It decides nothing.

Why two blocks

The two blocks match what the FPGA builds: LUTs that work out next, and flip-flops that hold state. Every decision is in the case, and the always_ff block never changes: adding a state means adding a case line. And next shows in a waveform where the machine will go at the next edge, before it goes. This course writes its state machines this way.

Questions

Question 1 of 3. Put the steps in order

In lesson 5.2's two-block door, put these in the order they happen when a closed door is pushed.

  • A rising edge of clk comes.
  • push becomes 1 while the door is closed.
  • The state register takes its new value.
  • is_open becomes 1.
  • next becomes OPEN.
Show answer and explanation

In order:

  1. push becomes 1 while the door is closed.
  2. next becomes OPEN.
  3. A rising edge of clk comes.
  4. The state register takes its new value.
  5. is_open becomes 1.

next is logic: it changes as soon as push does, before any edge (lesson 5.2). The state register waits for the rising edge, then takes next, and is_open, which depends only on the state, follows at once. Putting the edge before next treats next as a register; it is the value the register is about to take.

Question 2 of 3. Put the steps in order

Put these steps of lesson 5.2's two-block door in order, from the first line of the next-state logic to the edge.

  • That line's if may give next another value.
  • At the rising edge, state takes next.
  • The case picks the line for the present state.
  • next is given the value of state.
Show answer and explanation

In order:

  1. next is given the value of state.
  2. The case picks the line for the present state.
  3. That line's if may give next another value.
  4. At the rising edge, state takes next.

The default line comes first, so the case can change next where a transition applies, and next keeps the state everywhere else (lessons 1.4 and 5.2). Only at the edge does the register take next. Placed after the case, the default line would undo every transition: next would always equal state, and the door would never move.

Question 3 of 3. Find the bug

This two-block door should behave like lesson 5.1's: it stays in its state until push or key moves it. Its testbench fails. Pick the line that is wrong.

  • 1// The door of lesson 5.1, in the two-block form. push should open a closed
  • 2// door and close an open one; key should lock a closed door and unlock a
  • 3// locked one. push and key are one-cycle pulses; push wins if both come
  • 4// at once.
  • 5module door2_bug (
  • 6 input logic clk,
  • 7 input logic rst, // at a rising edge: the door is closed
  • 8 input logic push,
  • 9 input logic key,
  • 10 output logic is_open,
  • 11 output logic is_locked
  • 12);
  • 13 typedef enum logic [1:0] {CLOSED, OPEN, LOCKED} state_t;
  • 14 state_t state, next;
  • 15
  • 16 // Next-state logic: the state the door goes to at the next rising edge.
  • 17 always_comb begin
  • 18 next = CLOSED; // unless a line below says otherwise
  • 19 case (state)
  • 20 CLOSED: if (push) next = OPEN;
  • 21 else if (key) next = LOCKED;
  • 22 OPEN: if (push) next = CLOSED;
  • 23 LOCKED: if (key) next = CLOSED;
  • 24 default: next = CLOSED;
  • 25 endcase
  • 26 end
  • 27
  • 28 // The state register.
  • 29 always_ff @(posedge clk) begin
  • 30 if (rst) state <= CLOSED;
  • 31 else state <= next;
  • 32 end
  • 33
  • 34 // Outputs from the state alone.
  • 35 assign is_open = (state == OPEN);
  • 36 assign is_locked = (state == LOCKED);
  • 37endmodule
Show answer and explanation

The bug is on line 18, next = CLOSED; // unless a line below says otherwise. It should read next = state;.

The first line of the next-state logic gives next the value CLOSED instead of state. So wherever no transition applies, the door goes to CLOSED at the next edge: an open door shuts itself and a locked one unlocks. Three other lines also end in next = CLOSED;, the two transitions and default, and those are right. Written next = state;, the default keeps the door where it is.
