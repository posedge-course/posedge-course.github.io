1.4 The accidental latch

Teaches Latch (primitive). About 6 minutes.

An always_comb block should describe logic: outputs that depend only on the inputs as they are now. That holds only if every path through the block gives every output a value. Listing 1 makes sure of it. It lights an RGB LED from three buttons, and the block's first line (line 12) turns all three colours off, so each if below only has to turn one on. The braces join the three signals into one, so one line sets them all.

A memory you did not ask for

Now suppose a path gives an output no value. The only meaning left is "keep the old value", and keeping a value is memory. That memory is a latch: while its enable is on, its output follows its input; while the enable is off, it holds its value.

Figure 1 simulates a copy of Listing 1 whose line 12 sets red and green but forgets blue. The only line that sets blue runs while BTN0 alone is pressed, so that is the latch's enable. Once it has turned blue on, no line turns it off.

Three signs give a latch away:

  • Verilator warns LATCH, as it does for this copy. Not every bug gets a warning: lesson 1.3's broken LED modes pass Verilator, and only the testbench finds the bug.
  • In simulation, a signal keeps a value it should not.
  • Vivado builds a latch and warns. A latch in combinational logic is almost always a mistake.

The fix

Give every output a value on every path. The surest way is a default assignment, as in Listing 1: a first line that sets every output, which the lines after it may change. Inside an always_comb block the lines are worked through in order, top to bottom, each time an input changes, so a later line can change what an earlier one set. With that line, synthesis builds Listing 1 from LUTs alone, with no memory.

The other way is to set every output in every branch and close every chain: end each if chain with an else, and each case with a default. An if chain often tests a select with ==, which is 1 when its two sides are equal, as in if (sel == 2'd0); end such a chain with a plain else.

Questions

Question 1 of 4. Predict blue

In rgb_select, the first line of the block turns every colour off. Then BTN2 gives red; if it is not pressed, BTN1 gives green; if neither is, BTN0 gives blue. Steps 0 and 1 are drawn for you. Set blue for the rest.

Question 2 of 4. Fill the blank

The first line of the block must turn red, green and blue off before the if lines run. Type the value it gives all three.

hdl/level-01/rgb_select/rgb_select.sv

1// The colour of an RGB LED from three buttons: BTN2 gives red; if it is
2// not pressed, BTN1 gives green; if neither is, BTN0 gives blue.
3module rgb_select (
4 input logic btn0,
5 input logic btn1,
6 input logic btn2,
7 output logic red,
8 output logic green,
9 output logic blue
10);
11 always_comb begin
12 {red, green, blue} = (blank); // all off; a line below may turn one on
13 if (btn2) red = 1'b1;
14 else if (btn1) green = 1'b1;
15 else if (btn0) blue = 1'b1;
16 end
17endmodule
Show answer and explanation

The blank is 3'b000. Also accepted: 3'b00, 3'b0, 3'd0, 3'h0, 3'o0, 'b0, 'd0, 'h0, 'o0, '0, 0.

3'b000 is three bits, all 0 (lesson 1.3's sized numbers): red gets the first, green the second and blue the third, in the order of the braces. After this line every colour has a value on every path, so no latch can form, and each if only has to turn one colour on.

Question 3 of 4. Predict led

In peek_bug, an always_comb block sets led to sw while peek is 1, and no line gives led a value while peek is 0. Set led for every step of this simulation.

Question 4 of 4. Find the bug

This block should pass a when sel is 0, b when sel is 1, and c for every other value of sel. Verilator warns LATCH. Pick the line that is wrong.

hdl/level-01/pick3_bug/pick3_bug.sv

  • 1// y is a when sel is 0, b when sel is 1, and c for every other value of
  • 2// sel.
  • 3module pick3_bug (
  • 4 input logic [1:0] sel,
  • 5 input logic a,
  • 6 input logic b,
  • 7 input logic c,
  • 8 output logic y
  • 9);
  • 10 always_comb begin
  • 11 if (sel == 2'd0) y = a;
  • 12 else if (sel == 2'd1) y = b;
  • 13 else if (sel == 2'd2) y = c;
  • 14 end
  • 15endmodule
Show answer and explanation

The bug is on line 13, else if (sel == 2'd2) y = c;. It should read else y = c;.

The last line is an else if, so it gives y a value only when sel is 2. When sel is 3 no line runs, y keeps its old value, and that memory is the latch. As a plain else, the line covers 2 and 3, as the comment asks. Verilator reports the latch at always_comb begin, the start of the block that builds it, not at the line that causes it. A default first line that sets y to c would also remove it: that is lesson 1.4's other fix.
