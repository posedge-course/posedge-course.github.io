2.2 always_ff and why assignments use <=

Teaches <= in always_ff (primitive). About 5 minutes.

Lesson 2.1 read <= as "becomes, at the edge". With one flip-flop that is enough. With two in a row, you need to know exactly what happens at the edge.

Listing 1 puts two flip-flops in a row: q1 takes d, and q2 takes q1. Both lines are in one always_ff block, which describes flip-flops: its lines run at each rising edge of clk, and only then.

Read first, then change

<= is a nonblocking assignment. At a rising edge, the simulator first works through the block reading the right-hand side of every <=, line by line, with the values from just before the edge. Only then does it give each left-hand side its new value, in the same order. Nothing reads in between, so the new values all appear at the same moment.

So q2 <= q1 reads q1 before q1 changes, and q2 takes the value q1 had before the edge. q1 is d one cycle late, and q2 is d two cycles late. Swap the two lines and nothing changes: every right-hand side is still read before any left-hand side changes.

The hardware works the same way. Figure 1 shows what Vivado builds from Listing 1: two FDREs on one clock, each taking at the edge the value its D input had just before it.

Why not =

= is a blocking assignment: its left-hand side changes at once, before the next line runs. That is what you want in always_comb (lesson 1.3). In always_ff, a line after it would read the new value. In a chain, the second flip-flop would take the first one's new value, and the two would merge into one. Verilator warns about = in always_ff.

The rule to keep: <= in always_ff, = in always_comb.

Question 3 of 4. Put the steps in order

Put in order what the simulator does in two_flops at one rising edge of clk, and after it.

  • q1 and q2 change to their new values, at the same moment.
  • The line for q2 reads q1.
  • The line for q1 reads d.
  • q1 and q2 keep these values until the next rising edge.
Show answer and explanation

In order:

  1. The line for q1 reads d.
  2. The line for q2 reads q1.
  3. q1 and q2 change to their new values, at the same moment.
  4. q1 and q2 keep these values until the next rising edge.

At the edge, the simulator first reads every right-hand side, line by line, with the values from just before the edge. Only then does it change the left-hand sides (lesson 2.2). So the line for q2 reads q1 before q1 changes, and q2 gets the old value. Nothing reads between the two changes, so in the hardware they happen at the same moment. If q1 changed before the line for q2 read it, as when software runs one line after another, q2 would equal q1: that is what = does. Between edges both keep their values, although d changes at the falling edge.

Question 4 of 4. Find the bug

This should be lesson 2.2's two flip-flops in a row, with q2 two cycles behind d. But synthesis builds only one flip-flop from it, and q2 always equals q1. Pick the line that is wrong.

hdl/level-02/two_flops_bug/two_flops_bug.sv

  • 1// Two flip-flops in a row: q1 is d one cycle late, and q2 is d two cycles
  • 2// late.
  • 3module two_flops_bug (
  • 4 input logic clk,
  • 5 input logic d,
  • 6 output logic q1,
  • 7 output logic q2
  • 8);
  • 9 always_ff @(posedge clk) begin
  • 10 q1 = d; // q1 takes d
  • 11 q2 <= q1; // q2 takes the value q1 had just before this edge
  • 12 end
  • 13endmodule
Show answer and explanation

The bug is on line 10, q1 = d; // q1 takes d. It should read q1 <= d;.

q1 = d; is a blocking assignment: q1 changes at once, so the next line, q2 <= q1;, reads the new q1, which is already d. q2 then always equals q1, and synthesis builds a single flip-flop that drives both outputs. Verilator warns BLKSEQ about this line. With q1 <= d;, the line for q2 reads q1 before it changes, and the chain has two flip-flops again. The q2 line is right as it is.
