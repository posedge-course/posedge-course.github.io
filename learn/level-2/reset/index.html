2.3 Reset: synchronous and asynchronous

Teaches Synchronous reset (primitive), Asynchronous reset (primitive). About 6 minutes.

A flip-flop holds whatever it took at the last rising edge. Often you want to put it back to a value you choose: when the design starts, or whenever someone presses a button to start again. A reset does that.

When the FPGA loads its bitstream (lesson 0.3), every flip-flop in this level's designs starts at 0. The simulator does not assume that: until a flip-flop's first edge loads a value, it shows the value as unknown, because the code never said what it starts at. A reset puts the start value in the code, and lets you start again at any time without loading the bitstream again.

Listing 1 has two flip-flops with the same d and a different kind of reset each.

Synchronous reset

The first block tests rst_sync before anything else: if it is 1, q_sync becomes 1'b0; if not, q_sync takes d. The block runs only at a rising edge, so rst_sync is looked at only then, like d. A pulse on rst_sync that comes and goes between two rising edges is never seen. This is a synchronous reset. Vivado builds it from an FDRE and joins rst_sync to its R input (lesson 2.1).

Asynchronous reset

The part in brackets after @ is the block's event list, also called its sensitivity list. The second block's has a second event, posedge rst_async, so the block also runs the moment rst_async rises, and q_async becomes 0 at once, without waiting for the clock. It stays 0 while rst_async is 1. Once rst_async falls, the flip-flop takes d again at the next rising edge. This is an asynchronous reset. Vivado builds it from an FDCE, a flip-flop whose clear input, CLR, works without the clock.

Figure 1 shows both resets rising in the middle of a cycle.

AMD's methodology guide recommends synchronous resets for these FPGAs, and this course uses them unless a lesson says otherwise.

Questions

Question 1 of 4. Predict q_sync

q_sync has a synchronous reset: at a rising edge where rst_sync is 1, it becomes 0; at every other rising edge, it takes d. Cycles 0 and 1 are drawn for you. Set q_sync for the rest.

Question 2 of 4. Predict q_sync

q_sync has lesson 2.3's synchronous reset. In this simulation some pulses on rst_sync are short, and some begin or end in the middle of a cycle. Set q_sync for every cycle.

Question 3 of 4. Put the steps in order

In resets, d is 1 and so is q_async. Then rst_async pulses for 2 ns between two rising edges, while rst_sync stays 0. Put in order what happens.

  • rst_async goes to 1, 1 ns after a falling edge of clk.
  • rst_async goes back to 0, 2 ns later.
  • The next rising edge of clk arrives.
  • q_async takes d again, and becomes 1.
  • q_async becomes 0.
Show answer and explanation

In order:

  1. rst_async goes to 1, 1 ns after a falling edge of clk.
  2. q_async becomes 0.
  3. rst_async goes back to 0, 2 ns later.
  4. The next rising edge of clk arrives.
  5. q_async takes d again, and becomes 1.

posedge rst_async is in the event list, so the block runs the moment the reset rises and q_async becomes 0 at once, without the clock (lesson 2.3). It stays 0 after the pulse, because nothing runs the block again until the next rising edge; there rst_async is 0, so q_async takes d. If you waited for the rising edge before clearing q_async, you treated it as a synchronous reset, and a synchronous reset would never have seen this pulse at all.

Question 4 of 4. Find the bug

This flip-flop should clear q the moment rst rises, without waiting for the clock. Its testbench fails. Pick the line that is wrong.

hdl/level-02/areset_bug/areset_bug.sv

  • 1// A flip-flop with an asynchronous reset: q becomes 0 the moment rst
  • 2// rises, without waiting for the clock, and stays 0 while rst is 1. At
  • 3// every other rising edge of clk, q takes d.
  • 4module areset_bug (
  • 5 input logic clk,
  • 6 input logic rst, // clears q at once
  • 7 input logic d,
  • 8 output logic q
  • 9);
  • 10 always_ff @(posedge clk) begin
  • 11 if (rst) q <= 1'b0;
  • 12 else q <= d;
  • 13 end
  • 14endmodule
Show answer and explanation

The bug is on line 10, always_ff @(posedge clk) begin. It should read always_ff @(posedge clk or posedge rst) begin.

The event list has only posedge clk, so the block runs only at rising edges and rst is looked at only then: a synchronous reset. The testbench's first failure is 1 ns after rst rises in the middle of a cycle, at 13 ns, where q is still 1. Written always_ff @(posedge clk or posedge rst) begin, the block also runs the moment rst rises, and q becomes 0 at once. The if (rst) line is right: it is what makes the reset win over d, in both kinds.
