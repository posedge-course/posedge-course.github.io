6.4 Reading the utilisation report

Teaches Utilisation report (design). About 5 minutes.

Every build in this level ended with a Utilization report. This lesson reads one table at a time, using mul16_nodsp: lesson 6.3's 16 by 16 multiplier, built with no DSP block allowed, so its product is all LUTs and carry chains.

Used, Available, Util%

Each row counts one kind of resource. Used is how many the design takes, Available how many the chip has, and Util% the first as a percentage of the second. Listing 1 is the Slice Logic table. A slice is one of the small groups of LUTs and flip-flops the chip is built from, which is why the rows say Slice LUTs and Slice Registers.

Slice LUTs splits into LUTs used as logic and as memory (lesson 6.3), and Slice Registers into flip-flops and latches. F7 and F8 Muxes are lesson 6.2's MUXF7s and MUXF8s. The tables after it count block RAM tiles, DSP blocks, pins and clock buffers, and the Primitives table at the end names every cell.

The LUT rows of the Primitives table can add up to more than Slice LUTs. A LUT6 can hold two smaller LUTs if they share their inputs, and Slice LUTs counts the LUT6s that hold them: for mul16_nodsp, 301, where its Primitives table lists 349 LUT cells.

After synthesis, after place and route

The course's builds write the report twice: utilization_synth.rpt after synthesis, and utilization.rpt after place and route. In Vivado's window you get the same two from Open Synthesized Design or Open Implemented Design, then Report Utilization. The first marks its LUT count with an asterisk and a note that the final count is usually lower: the steps after synthesis tidy the netlist, merging and removing cells. For mul16_nodsp, synthesis counted 337 LUTs; the count in Listing 1 is the final one. Read the report after place and route when you want to know what the design takes.

Rows that should be zero

A count where you expected none is a clue. Register as Latch counts latches, and a design that should have none tells you that some block leaves a value unassigned (lesson 1.4). The timing summary, Vivado's report on timing, notices too: Vivado times a latch's gate like a clock, and when no clock reaches it, it reports a register with no clock, which level 7 looks at.

Question 1 of 3. Read the report

Vivado put the product of lesson 6.3's mul16 in one DSP48E1. Below is the DSP table of its Utilization report.

vivado/reports/mul16/arty-a7-100t/utilization.rpt, lines 112 to 117. Written by Vivado.

112+----------------+------+-------+------------+-----------+-------+113|    Site Type   | Used | Fixed | Prohibited | Available | Util% |114+----------------+------+-------+------------+-----------+-------+115| DSPs           |    1 |     0 |          0 |       240 |  0.42 |116|   DSP48E1 only |    1 |       |            |           |       |117+----------------+------+-------+------------+-----------+-------+

How many DSP blocks does the chip have?

Show answer and explanation

The report says 240.

Read the DSPs row across to Available: 240, the DSP48E1s on this chip, whatever the design uses. mul16 uses 1 of them, so its Util% is 1 ÷ 240 × 100 = 0.42.

What is the Util% of mul16_nodsp's Slice LUTs?

Show answer and explanation

The report says 0.47 %.

Read the Slice LUTs row across to Util%: 0.47. The product takes 301 of the chip's 63,400 LUTs, and 301 ÷ 63,400 × 100 = 0.47, about half of one percent. With a DSP block allowed, mul16 took no LUT at all, and one of the 240 DSP blocks.

Question 3 of 3. Find the bug

peek_bug is level 1's LED that should show sw while peek is 1 and be 0 while peek is 0. Vivado built it, and its Slice Logic table counts one Register as Latch, where this design should have no register at all. Pick the line that makes the latch.

hdl/level-01/peek_bug/peek_bug.sv

  • 1// led shows sw while peek is 1, and should be 0 while peek is 0.
  • 2module peek_bug (
  • 3 input logic peek,
  • 4 input logic sw,
  • 5 output logic led
  • 6);
  • 7 always_comb begin
  • 8 if (peek) led = sw;
  • 9 end
  • 10endmodule
Show answer and explanation

The bug is on line 8, if (peek) led = sw;. It should read if (peek) led = sw; else led = 1'b0;.

if (peek) led = sw; gives led no value while peek is 0, so led must keep the value it had: a latch (lesson 1.4), which the report counts among its registers. An else that sets led to 0 gives it a value on every pass through the block, and the latch goes.
