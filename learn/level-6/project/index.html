Level 6

Level 6 project One multiplication written two ways

Write mul16 in my_mul16.sv and mul_shift16 in my_mul_shift16.sv until both provided testbenches print TEST PASSED, then compare the cells and the speed of the two. About 60 minutes in simulation.

A multiplication can be one line of code, or a small machine that works it out over many cycles. This project writes it both ways and compares them: the cells each one takes, and how many products each makes in a second. It uses lesson 6.3's DSP blocks, lesson 6.2's carry chains, and level 5's controller with a datapath.

The first way: one *

The ports of mul16
PortDirection and widthWhat it is
clkinput, 1 bitthe clock
a, binputs, 16 bits eachthe numbers to multiply, from 0 to 65,535
poutput, 32 bitsa times b, from the last rising edge

The product of two 16-bit numbers needs 32 bits: 65,535 × 65,535 is just under 2³².

The second way: shift and add

Multiplying by hand, you multiply by each digit of one number, shift each result one place further left, and add them up. In binary each digit is 0 or 1, so each step either adds the shifted number or adds nothing. mul_shift16 does one step per clock cycle: 16 steps for the 16 bits of b.

The ports of mul_shift16
PortDirection and widthWhat it is
clkinput, 1 bitthe clock
rstinput, 1 bitat a rising edge where it is 1, the controller goes to IDLE
startinput, 1 bita one-cycle pulse that starts a job; ignored while busy is 1
a, binputs, 16 bits eachthe numbers, read at the edge that takes start
poutput, 32 bitsthe product, once done is 1
busyoutput, 1 bit1 during the 16 steps
doneoutput, 1 bit1 from the end of the job until the next start

The files you write are my_mul16.sv and my_mul_shift16.sv; the modules inside are mul16 and mul_shift16, the names the testbenches use.

The course built three designs: mul16, the same mul16 with no DSP block allowed (lesson 6.4's mul16_nodsp), and mul_shift16. Here are their Primitives tables.

What you see when it works

  • Both runs print TEST PASSED.
  • In the waveform, busy is 1 for 16 cycles, and done comes on the 17th cycle after the edge that took start.
  • The comparison: mul16 is one DSP48E1 and no other cell but the pin and clock buffers. mul16_nodsp has 349 LUT cells (301 Slice LUTs, lesson 6.4), 43 CARRY4s and 32 FDREs. mul_shift16 has 73 LUT cells (70 Slice LUTs), 8 CARRY4s and 87 FDREs: against mul16_nodsp, about a fifth of the LUT cells for nearly three times the flip-flops, because it keeps addend, bits, the step count and the state as well as p.
  • The working-out: mul16 makes 100,000,000 products a second, one at every edge. mul_shift16 needs 16 cycles of BUSY and one of DONE, in which the next start can come, so one product every 17 cycles: about 5,900,000 a second.

If it fails

  • syntax error, followed by Invalid module instantiation: the command lacks -g2012. Add it.
  • TEST FAILED: p changed before a rising edge at 11 ns: p is worked out with an assign, not kept in a register. Give it its value in an always_ff block.
  • warning: Port 4 (p) of mul16 expects 16 bits, got 32, then TEST FAILED: 65535 times 65535 gave 1 at 30 ns: p is 16 bits wide. A product of two 16-bit numbers needs 32.
  • TEST FAILED: busy=0 done=1 in step 15 at 190 ns: the job ends one step early. BUSY must last until the step count reaches 15, the sixteenth step.
  • TEST FAILED: 6 times 7: p=10 busy=0 done=1: addend moves the wrong way. It must move left, one place each step.
  • TEST FAILED: 6 times 7: p=x busy=0 done=1: p is not set to 0 when a job starts.
  • TEST FAILED: 6 times 7: p=0 busy=0 done=1: each step tests the wrong bit of bits. It must be bit 0, which the shift right brings each bit of b into in turn.

These messages are from Icarus Verilog 12.

On the board (optional)

You need an Arty A7 and Vivado for this part. Everything above works without them.

The board steps use Vivado's project mode, as in the earlier projects. The saved constraints files give a and b the four Pmod headers and p the chipKIT header, so with nothing plugged in, the builds are only for their reports.

When both builds finish, compare each Primitives table with the course's, Listings 1 and 3 above. If a count differs, compare your code with the course's answer after the checklist.

Your checklist

Simulation path

  1. Make a new folder and save mul16_tb.sv and mul_shift16_tb.sv into it from the list above. Each is the specification of one way, and reads only the ports.
  2. Make a file my_mul16.sv with a module named mul16 and the four ports in the first table. Inside, one always_ff block gives p the product a * b at each rising edge: the register is part of the specification.
  3. Run iverilog -g2012 -o mul16_sim mul16_tb.sv my_mul16.sv, then vvp mul16_sim, until it prints TEST PASSED.
  4. Make a file my_mul_shift16.sv with a module named mul_shift16 and the eight ports in the second table. Give it a controller in the two-block form (lesson 5.2) with the states IDLE, BUSY and DONE, as lesson 5.4's mul_repeat has: start takes IDLE or DONE to BUSY, and BUSY goes to DONE after 16 steps.
  5. Add the datapath. On start from IDLE or DONE, set p to 0, a 32-bit addend to a, a 16-bit bits to b, and a 4-bit step count to 0. At each edge in BUSY, add addend to p if bit 0 of bits is 1; then move addend one place left, move bits one place right, and add 1 to the step count.
  6. Make busy 1 in BUSY and done 1 in DONE. Then run iverilog -g2012 -o shift_sim mul_shift16_tb.sv my_mul_shift16.sv and vvp shift_sim until it prints TEST PASSED.
  7. Open mul_shift16_tb.vcd and add start, p, busy and done from mul_shift16_tb. Find the first job, 6 times 7, and count the cycles from the edge that takes start to the first cycle with done at 1.
  8. Read the three tables under "What Vivado built" above. For each design, add up its LUT rows to get its LUT cells, and write down its FDREs, CARRY4s and DSP48E1s.
  9. At 100 MHz, work out how many products each design can make in a second: mul16 one at every edge, mul_shift16 one per job, starting the next job in its DONE cycle. Then compare with "What you see when it works".

On the board (optional)

  1. In Vivado, create an RTL project for xc7a100tcsg324-1 with my_mul16.sv and the saved mul16.xdc, and a second one with my_mul_shift16.sv and mul_shift16.xdc. These builds are for their reports: a, b and p go to headers with nothing plugged in, so you need not program the board.
  2. Run Generate Bitstream in each, then Report Utilization (as in level 1's project). Compare your Primitives tables with the course's above: a different count means your code describes something different.
