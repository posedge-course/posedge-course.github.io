Reference

Works in simulation, dead on the board

A testbench proves that your code does what the testbench expects. When the board then does nothing, the difference lies somewhere between the testbench and the board. Check in the order the build goes: each check rules out a whole stage before the next.

1. The testbench

  • Run it once with the parameters the board build uses, not only the small ones that keep a simulation short. A count too large for its counter, say, shows only with the board's numbers.
  • Drive each input as the board drives it. The Arty's push buttons read 1 while pressed and 0 the rest of the time, so hold a reset at 0 except for short presses. A reset written for the other kind of button holds the design in reset for as long as nobody touches it, and a testbench that drives it the same wrong way still passes.
  • Check after every cycle, with !==, so that an X fails instead of slipping past the check.
  • Find the cause of any X in the waveform: a register with no start value, or a signal that nothing sets.
  • Keep # delays out of the design: synthesis drops them. Count clock cycles instead.

2. The Utilization report after synthesis

  • Register as Latch should be 0. A latch means an always_comb path gives an output no value.
  • Your logic should all be there. Synthesis removes a register that nothing reads, with the logic that only fed it; Verilator warns about it first, as a signal that is never used.

3. The timing summary after place and route

  • no_clock should be 0, with a create_clock for the board's clock, at its real period: 10 ns for the Arty's 100 MHz oscillator. With no clock, Vivado checks no path at all; with the wrong one, it checks the wrong clock.
  • Every constraint should be met: the timing summary says "All user specified timing constraints are met.", with WNS and WHS 0 or more. A failing path still builds, and on the board the flip-flop at its end may take a wrong value.
  • Every register should run on a clock the constraints describe. A clock made from a counter bit is a trap: keep one clock, and use a tick as an enable instead.
  • Every input from a button, and every single signal from another clock, should go through a synchroniser before anything reads it. A value from another clock crosses with a handshake or an asynchronous FIFO (lessons 9.3 and 9.4).

4. The pins

  • Each port on the pin the board wires to its part, with its I/O standard. The bitstream step stops if a pin or a standard is missing, but it cannot know you picked the wrong pin.
  • The master XDC counts its LEDs from 0: its led[0] is the LED marked LD4.
  • In the master XDC's serial names, rxd and txd are from the PC's point of view and _in or _out from the FPGA's: uart_rxd_out is the FPGA's output, the line the PC receives on.

5. The board

  • The bitstream must be built for your board's part: an Arty A7-35T and an A7-100T need different builds.
  • After Program Device, the board's DONE LED lights. A design programmed over USB lasts until the power goes off.
  • A serial terminal must listen at the design's baud rate, 115,200 in this course, with 8 data bits, no parity and 1 stop bit, or it shows the wrong characters, or none.

Then look inside

If every check passes and the board still misbehaves, the cause is often something the testbench never did. An integrated logic analyser records chosen signals on the chip itself, as it runs, and shows them as a waveform.
